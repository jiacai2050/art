# ART 线程优先级与锁公平性深度解析

本文分析了 Android Runtime (ART) 中 `synchronized` 锁的公平性，以及它如何处理线程优先级与优先级反转问题。

## 1. 核心结论
ART 的 `synchronized` 实现是 **非公平的 (Non-fair)**。在释放锁时，系统不会根据 Java 线程优先级（Java Priority）来选择下一个获取锁的线程。其核心目标是最大化系统吞吐量，而非保证绝对的优先级顺序。

## 2. 为什么解锁不按优先级排序？

### 2.1 Thin Lock 阶段 (无竞争)
*   **机制**：基于 CPU 原子指令 CAS。
*   **行为**：当锁释放时，所有竞争线程都在用户态发起 CAS。谁的指令先被硬件执行，谁就获胜。硬件层面的“先到先得”完全忽略了软件层面的优先级。

### 2.2 Fat Lock 阶段 (有竞争)
*   **机制**：基于内核 Futex。
*   **行为**：`Monitor::Unlock` 会调用 `FUTEX_WAKE` 唤醒等待者。
*   **内核调度**：Linux 内核的 Futex 队列通常遵循 **FIFO** 顺序。虽然内核调度器在分配 CPU 时间时偏向高优先级线程，但在“唤醒”这一动作上，它并不支持根据 Java 优先级对等待队列进行重排。

## 3. ART 的补救措施：手动优先级提升

虽然锁本身是不公平的，但 ART 意识到**优先级反转 (Priority Inversion)**（高优先级 A 等待低优先级 B）会严重损害体验。因此，ART 引入了手动干预机制：

*   **临时提速**：ART 可能会检测到当前线程正在执行关键的运行时操作。如果该线程的 Niceness 值较大（优先级低），ART 会**临时将其 Niceness 设为 0**（正常优先级）。
*   **恢复逻辑**：在关键操作完成后，ART 会检查 Niceness 是否仍为 0，如果是，则恢复为其缓存的原始优先级。
*   **目的**：这确保了即使低优先级线程持有了锁，它也能尽快跑完临界区，从而让高优先级等待者尽快拿到锁。

## 4. 关于 PI Futex (优先级继承) 的技术障碍

PI Futex 是一种理想的解决方案（A 等 B 时，B 自动获得 A 的优先级），但 ART 目前未启用，原因包括：

1.  **内核限制**：Linux 内核直到 **6.12** 版本才开始支持非实时线程（Non-RT）的优先级继承。
2.  **锁结构不兼容**：PI Futex 要求锁的状态位必须严格符合内核规范。而 ART 的 `LockWord` 采用了高度压缩的位设计（包含 GC 标记、状态位等），若要支持 PI Futex，需要对整个锁系统进行重大重构。
3.  **不可见性**：对于 `java.util.concurrent` 中的锁（基于 `park/unpark`），由于内核无法感知“谁在等待谁”，因此 PI 机制完全无法工作。

## 5. 关键警告：实时调度 (SCHED_FIFO)

在 Android 系统中，某些关键线程会被框架提升为 `SCHED_FIFO`。
*   **风险**：这种线程不会被普通线程抢占。
*   **死锁预防**：如果 `SCHED_FIFO` 线程在循环中自旋（如使用 `sched_yield()`）等待锁，会由于锁持有者（普通线程）永远得不到 CPU 而导致**系统永久死锁**。
*   **要求**：因此，所有涉及锁的代码必须使用内核提供的等待原语（如 Mutex, `Object.wait()`），确保线程在等待时能真正进入休眠。

## 6. 开发者指南

1.  **不要依赖优先级**：Java 优先级只是对内核的一个“建议”，不能作为同步逻辑的可靠依据。
2.  **避免长时间持锁**：缩短临界区是解决优先级反转的最有效手段。
3.  **标准 API 优先**：使用 `Thread.setPriority()` 而非 JNI 直接修改，以确保 ART 的优先级缓存机制正常工作。
